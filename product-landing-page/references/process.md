# 设计与开发过程

按时间顺序记录这次官网从无到上线怎么做的、每一步为什么这么选、哪里返工过。照着走能少绕弯。

## 一、设计

1. 先把要求翻译成可检查的约束。这次的要求是：与产品本身风格一致；功能介绍足够凝练；参考同类前沿产品的官网（首屏一句主张，下面是短小的功能格子，每格只有一句话）；画面要精致。每条都对应一个能检查的结果：同一套令牌、每个功能一句话、有一个让人记住的元素。
2. 动手前先写设计方案：4 到 6 个命名颜色、字体及分工、版面的一句话描述加线框、几条原则。然后拿它对照一遍「生成页面的常见套路」，有就改：米色底加衬线标题加陶土色强调；近黑底加一个荧光强调色；整页同一圆角同一阴影的卡片；每个标题上方一行全大写小标签。本次需求明确要求「与产品风格一致」，所以沿用系统灰阶是选择而不是默认。
3. 只在一个地方放胆：吉祥物坐在窗口边缘，可点击切换四种状态。其余部分刻意安静，不加渐变装饰，不做进场动画。
4. 窗口和功能片段用 HTML 画。画之前先列产品里真实存在的界面元素和文案，再照着搭，这样页面和应用不会各说各话。
5. 做完用截图逐状态检查。浅色、深色、窄屏各看一遍。本次深色模式只写了变量，没有真正目视检查，这是留下的缺口：下次构建完先看深色。

## 二、开发

1. 三个文件不加构建：`index.html`、`styles.css`、`app.js`。需求是一页静态展示，构建链只会增加部署负担。
2. 交互状态用一张表驱动。`POSES` 是一个对象，每种状态一条：说明文字、状态文字、是否在录制。一个 `setPose(name)` 同时更新主角图的显示、按钮的 `aria-pressed`、说明、状态点。按钮和主角点击都走同一个函数，不会出现三处状态不一致。
3. 下载按钮只认 `data-download` 属性，地址由 `app.js` 顶部一个常量填。换安装包只改一行。
4. 样式从一开始就按扫描规则写：一行一条声明、4 空格缩进、单引号。第一版写成了紧凑形式，提交后扫描一次报出 220 条，全是格式问题，不是逻辑错误。用 `scripts/css-expand.py` 展开后，去空白比对确认语义没变，再提交。
5. 下载信息返工过一次：写死的下载链接指向旧版本，而服务器上已经是新版本，安装包大小文字也要跟着改。之后的做法是发布前先读发行清单，再逐处替换页面里的版本、大小、链接。后来链接改成同域 HTTPS 的固定路径，由发布步骤把它指向当前安装包，页面就不用再跟版本走。
6. 提交只暂存自己改的文件，按文件名添加。工作区里出现过一处不是自己改的空白变动，没有把它带进提交，也没有去还原，而是告诉了用户。
7. 部署见 [static-deploy.md](static-deploy.md)。上线后核对每个资源返回 200 和下载链接的大小。域名前有单点登录网关时，匿名请求只会得到 302，需要登录态下看一次。

## 三、留下的缺口

- 深色模式没有目视检查。
- 页面里虚构的示例内容没有标注为示例。
- 安装包没有公证，页面没有写首次打开的处理方式。
- 服务直接暴露在明文 HTTP 上，只靠前面的网关做认证。
